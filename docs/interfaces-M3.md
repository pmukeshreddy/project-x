# M3: pinned Docker environment and saved-source lifecycle

The production API is `feature_rl.environments`. It supports pinned Python wheel profiles on Linux arm64/amd64, with Click 8.3.3 as the legacy default and no services. `EnvironmentRecipe`, `CommandSpec`, `ResourceLimits`, `AllowedChanges`, `SourcePair`, and `ArtifactRef` are the M0 contracts. M3 adds strict local runtime models, bounded archive handling, and an owned Docker lifecycle. It does not execute submitted Python on the controller.

## Construction and joins

Instantiate a controller-role `ArtifactStore`, then `DockerEngine(state_root=..., socket_path=..., policy=..., image_repository='registry.example.com/team/runtimes')`. `state_root` is private controller state and must persist across controller restarts. `engine.qualify_boundary()` must succeed before `EnvironmentRuntime(store=store, engine=engine, revision=<40-or-64-hex implementation identity>)` accepts historical/candidate work. Qualification machine-checks actual kernel denials and effective Docker settings. Missing images are pulled by immutable digest; missing daemon, failed pull or failed qualification rejects. There is no host-execution fallback.

`create_recipe(baseline, pins, source_evidence=...) -> PreparedEnvironment` validates the configured `RuntimeProfile`, exact dependency wheel hashes and baseline manifest. `create_click_recipe(...)` remains the Click-specific entry point. The policy image pins the OS userspace, interpreter and system packages; optional `RuntimeProfile.system_packages` entries declare exact Debian package names/versions, checked against that base. Supply a base containing those packages and a complete wheel closure including build requirements. Missing/incompatible pins, missing system packages, unsupported wheels or an offline baseline build failure reject construction before a recipe is published. No host packages are installed.

Construction generates and retains a canonical source-free Dockerfile/build-context artifact, installs the hash-checked wheels with networking disabled, and publishes the image to `image_repository`. This requires Buildx/BuildKit with `SOURCE_DATE_EPOCH` and timestamp-rewrite support, plus registry push access. The recipe uses a registry manifest digest, never a tag or Docker config ID. The context SHA256 includes the base digest, platform, profile, installer/checker recipe and wheel bytes. Its registry tag enables shared cache lookup; a durable local record pins the selected digest. The existing state lock serializes constructors sharing a state root. Subsequent construction reuses that image; rollouts never build it. Retain the registry manifest/layers and CAS context for reproducibility. Registry errors fail closed rather than trigger a replacement build. Construction cache tags must be controlled by the trusted builder.

New recipes carry an optional `runtime_image` reference and link their context plus safe baseline-validation summary. Older recipes without that field retain their serialized identities and original setup commands. The default legacy base remains `feature-rl-m3-less@sha256:b28d3b1eeaa6251e82354fa61dc28a29afead9e2d7179436e77ca8ba612032fa`; constructing from this historical, locally retained base requires it on the builder. Newly published images are independently pullable by workers.

Workers need Docker and the recorded `host_requirements`: matching Linux architecture, Docker runtime, and no GPU for this supported track. They can call `engine.qualify_boundary(image=recipe.image_digest)` to qualify using only the final image. They need neither the base image nor Buildx nor a publishing repository. The existing dedicated Docker client config under `state_root/docker-client` also governs registry credentials; ambient user Docker settings are not imported. Each fresh sandbox links `/workspace/deps` to the image's read-only `/opt/feature-rl/deps`; source/wheel staging and candidate builds remain isolated as before. GPU devices/drivers and other host capabilities remain unsupported and are never installed or changed by construction.

`PreparedEnvironment` contains the recipe and policy CAS references. The recipe binds the exact image, dependencies, setup/reset commands, source-only dependency policy, environment, resource limits and neutral repair artifact. `recipe(prepared)` reloads and verifies those joins and the dependency bytes. `SourcePair` remains private. The full qualification includes private controller diagnostics; the authoring recipe links only a qualification summary without controller socket/state paths, ownership tokens, or private source refs.

`open_workspace(prepared, source=None, role='baseline', source_pair=None, allowed_changes=None) -> WorkspaceHandle` creates a fresh persisted saved-source workspace. Baseline must equal the recipe's B input; reference requires an actual M1 `SourcePair` joining that same B and exact H ref. Candidate source is checked against B using `AllowedChanges`. Only `src` and its subdirectories can be change roots for this recipe; dependencies, pyproject/locks/tests and additional artifact types remain immutable. H is never part of shared setup. Caller roles and private references remain controller concerns; never expose this service's private store/state directory to a worker.

Archive reads use M0 `get_bytes(max_envelope_bytes=..., max_payload_bytes=...)`; structured reads use `get_artifact(max_envelope_bytes=...)`. M3 additionally caps aggregate wheel/staging bytes, archive files/expanded bytes and wheel expansion. Source archives are inert PAX tar, regular files only, at most 1024 UTF-8 path bytes and 255 bytes per component. Traversal, absolute paths, links, sparse files, duplicates, history/cache paths and file-ancestor collisions are rejected. Controller hashes cover canonical archive bytes and a sorted path/content/executable-bit tree manifest. SHA256 in an `ArtifactRef` identifies the CAS envelope; raw archive/wheel SHA256 fields identify bytes and are deliberately separate.

## Two command paths

`execute_development(handle, ExecutionRequest(command=CommandSpec(...), stdin=b'', save_source=True)) -> ExecutionResult` works without a successful candidate build. Each call stages the latest confirmed source into a fresh container and links the image's prebuilt dependencies; legacy recipes retain offline dependency installation. The profile's development `PYTHONPATH` (for Click, `/workspace/source/src:/workspace/deps`) makes a subsequent import/test process within that command observe the current source. It does not install the target project. A syntax/build error therefore cannot prevent an ordinary file inspection or repair command. Within one Python interpreter, normal Python module caching still applies: edits do not magically reload an already imported module. Source edits are captured on an ordinary process exit, including a nonzero exit. Process state and non-source files do not persist between calls.

`build_snapshot(handle) -> BuildResult` builds the latest confirmed source in a fresh container using the recipe's fixed dependencies and `pip wheel --no-build-isolation --no-deps --no-index`. All package hooks run in that worker. The controller reads a bounded wheel and requires its source file map to equal the supplied bytes under the profile's source mappings exactly; other files must stay within the exact project dist-info root. It publishes a private per-source wheel, source/recipe/policy/tree bindings, successful cleanup evidence and a partial measured construction cost. No target wheel becomes a reusable shared dependency.

`execute(handle, request, build=BuildResult) -> ExecutionResult` is the installed-wheel path for discovery/grading orchestration. It requires the build's exact current source/recipe/policy/tree, raw wheel hash, wheel contents and successful build receipt. It stages and installs that wheel in a *different fresh container*, after the build container has been removed. `PYTHONPATH=/workspace/site:/workspace/deps`, `PYTHONSAFEPATH=1`, the observed absence of any user-site entry, and disabled bytecode writes keep the development/test source out of the default package import path. Tests can run with cwd `/workspace/source`; adapters should use `/workspace`. This path deliberately requires an explicit rebuild after a saved edit. Candidate commands and candidate import reports remain untrusted observations; M4 must keep private comparisons outside the worker and must not equate a printed import path or public pytest success with a reward.

`ExecutionRequest.remaining_cpu_seconds: float | None = None` optionally lowers the cumulative worker CPU stop threshold for either command path. A supplied value must be finite, positive and no greater than the admitted `SandboxPolicy.cpu_seconds`; omission retains the policy cap. Staging, dependency setup, the requested command, in-container observation probes and source export share the same cgroup counter and monitor. A final poll after ordinary command/export completion prevents committing source when that poll observes exhaustion. The exact effective value is persisted as `record.binding.effective_cpu_seconds` and recorded numerically as `effective_cpu_seconds` in execution/export receipts. CPU exhaustion during staging/setup/export returns `cpu_limit` / `candidate` and the last confirmed source; monitor, storage and cleanup faults retain infrastructure attribution. This is the existing sampled watchdog, with detection/probe/cleanup overshoot, not an exact kernel CPU-time quota or controller/GPU budget. Cleanup is always attempted even after exhaustion. M7 should pass its remaining budget and retain actual measured costs and this uncertainty.

Commands use argv tuples, no implicit shell, bounded serialized stdin, separate binary stdout/stderr and a cwd within `/workspace`. A caller can explicitly invoke a shell *inside* the sandbox. Locale is C.UTF-8, timezone UTC, hash seed 0, plugin autoload disabled. Build and installed execution commands are in the recipe; the explicit development import policy is in runtime evidence. Six wheel hashes remain frozen, including flit_core 3.11.0 as a disclosed neutral reconstruction pin.

## Save, reset, limits and recovery

`SavedSource` contains artifact/raw/tree hashes, version and UTC saved time. The workspace additionally persists its monotonically changing generation and source/recipe/policy/role/SourcePair/AllowedChanges identity. Ownership is written before Docker create and rechecked under the controller operation lock. Each operation persists a unique container name, owner token, daemon ID and resulting container ID. Admission rejects a changed workspace generation. The state lock serializes operations in one runtime root; concurrent operations fail explicitly rather than sharing mutable workers.

Saving means a controller-validated **last-confirmed capture**, not an atomic filesystem instant. A fixed `python -I` exporter reads through dirfds without following links, checks file type/count/size and before/after file metadata, and returns bounded tar bytes. The controller independently revalidates the archive and allowed changes, publishes the canonical source and durably records it before calling the new version saved. The receipt contains the export start/end interval. Directory races or modifications after capture cannot retrospectively change those saved bytes.

On timeout, CPU/output/memory limits, unavailable capture, invalid export or interruption, the last confirmed snapshot remains attributable and available. Unsaved changes from that command may be lost. Do not assume a periodic autosave or infer a new source submission from a destroyed tmpfs. `save_source=False` explicitly keeps the previous saved version. A nonzero ordinary command exit can still save valid edits. Deleting the source root, unsupported links and source size overflow yield a candidate `source_rejected`, not an invented daemon failure.

`reset(handle) -> SavedSource` first recovers any pending owned cleanup, then restores the exact initial source. Saved versions are relative to that snapshot generation: reset returns its original version/time while the workspace generation increases. `close(handle) -> SavedSource` marks it closed after recovery and advances its generation. Both close and reset acquire the operation lock before reading/checking workspace state and hold it through the durable write. Under that same lock they first require every owned operation in this runtime root to have a verified `removed` record. If an intervening operation left cleanup pending after the earlier recovery, terminal admission raises `CleanupUnverified` without changing source, generation or closed state. Call `recover_owned()` and retry; the admission check never converts pending state into an absence claim. A save that finishes before that lock is acquired is observed by the terminal transition; overlap while the lock is held fails explicitly. Reset always advances the latest generation, even when the restored source bytes are identical, so an older pending execution cannot pass admission after a second reset. There is no persistent running container after a completed call. `recover_owned() -> list[dict]` reads the durable operation records, checks the live daemon and exact owner/operation labels, force-removes only matching owned containers and verifies the specific Docker absence response. It works after controller loss and when the direct exec/attach client exited before descendants. Daemon inaccessibility, mismatched identity or uncertain absence leaves cleanup pending and fails closed. Cleanup also runs when the state publication path fails; a failure to durably confirm cleanup cannot return an ordinary success.

Default limits: 0.5 CPU rate, 60 cumulative CPU seconds, 512 MiB memory with no swap, 64 pids, 128 MiB total writable space (119 MiB workspace, 8 MiB tmp, 1 MiB shm), 2 MiB aggregate ordinary worker stdout+stderr, 1 MiB command stdin, 8 MiB expanded source, 16 MiB archive, 2000 source members and 32 MiB aggregate staging. The root is read-only; writable mounts are noexec/nosuid/nodev. All caps are dropped; nonroot, no-new-privileges, private PID/IPC/cgroup/network namespaces and the explicit pinned seccomp profile apply. No host mounts, Docker socket, host home or private store enter the container.

The operation deadline is 120 seconds, with a separate bounded 10-second cleanup allowance and up to 5-second control/export operations clipped to the remaining operation deadline. Stdin is nonblocking; EOF is not process exit; Docker client group cleanup is unconditional. CPU rate and memory/pids/disk are kernel controls. Cumulative CPU seconds are externally monitored from Docker cgroups about every 0.2 seconds and can overshoot by sampling/control latency; they are not described as a kernel CPU-time quota. Ordinary stdout/stderr share the operation budget, including setup; source export has a separate bounded archive allowance. Cgroup OOM events observed around execution distinguish actual memory limits from a bare exit137. Docker control diagnostics have separate fixed bounded caps. Controller CAS/state retention has no automatic pruning and must be budgeted by its caller; per-operation temporary writable disk is bounded.

## Outcomes and publication faults

`ExecutionResult` includes operation ID, strict reason/failure category, command exit/stdout/stderr, observed maximum memory, OOM observation, pre-removal container state, verified cleanup, exact saved source/save status, private evidence ref and partial measured `CostRecord`. The container's PID1 exit state is distinct from the candidate exec exit. `failure_category` is `none`, `candidate`, `infrastructure` or `unresolved`; it is not a grading verdict.

Ordinary command failures and command resource limits are candidate observations. Invalid source capture is `source_rejected`; capture interruption without reliable attribution is `source_unavailable`/`unresolved`. Trusted setup, monitor, daemon, storage and cleanup faults are infrastructure failures. `BuildFailed` carries reason, failure category, cleanup status, saved source and full build evidence; it does not classify a daemon/cleanup failure as a valid candidate build failure. Receipts retain actual command outputs and maximum resource samples, including failed phases. Construction/execution wall and CPU measurements are partial; no inferred USD or GPU measurement is substituted for unknown values.

`EvidencePublicationFailed` is a typed infrastructure exception with bounded pending bytes, byte hash, artifact kind/visibility and available saved-source/cleanup context. `retry_publication(error)` retries those exact bytes without executing the command again. An unpublished result is not a successful ordinary receipt; consumers must resolve publication or keep it as an infrastructure failure. Other invalid API inputs fail before worker execution with `PolicyRejected`, `SourceRejected`, or upstream typed bounded-store errors. `DockerUnavailable` and `CleanupUnverified` never prove absence or candidate failure.

Local-service/networked tracks, Redis semantics and GPU environments remain unsupported. Runtime construction uses explicit pinned Python profiles and pre-supplied wheels/base images; automatic dependency acquisition, arbitrary language builders and host provisioning are outside this API.
