# M3 fix round 2: protected terminal cleanup admission

The connected P2 from [round2 review](../reviews/M3-production-round2.md) is fixed. Product base is `ad154f88013200d9c0134b808c9211032ed67a2b`; independent report/diagnostic were supplied at `4f506e3`. The original round1 source/generation fix remains intact. This handoff contains only necessary M3 product/tests, API clarification and new fix evidence; scoped independent re-review is pending.

Close/reset previously ran recovery, released its lock, then acquired a separate lock for the terminal transition. A development operation in that interval could leave a running owned container with `cleanup_pending` after a real cleanup fault. Terminal source/generation handling was protected, but it could still return normally without verifying that newly pending cleanup.

Both methods now check owned operation records while holding the same operation lock used for their workspace read/check/write. Any record not in verified `removed` state raises `CleanupUnverified` before reading or modifying workspace state. The existing recovery path still verifies daemon identity, exact ownership, actual removal and specific absence. The new check does not remove containers or rewrite records; it requires the caller to recover and retry when cleanup became pending after the initial recovery. Overlaps remain nonblocking, and no new lifecycle or lock mechanism was introduced.

The new parameterized regression exercises close and reset with the exact recovery-to-admission schedule. A real synthetic development command saves `x=42`, then its existing cleanup path encounters a deliberately missing Docker CLI endpoint. The real daemon is never stopped or reconfigured. After restoring the route, the test observes the exact owned container running and its record pending. The paused terminal transition resumes and must fail, leaving the complete workspace record unchanged, including the newly confirmed source. Subsequent recovery must remove the container; HTTP inspection must return404; the intended retry must then return the appropriate source and advance the latest generation once.

On the old product, **2 tests failed in 9.49s** because both terminal methods returned normal saved-source results with pending live ownership. After the fix, **2 tests passed in 8.38s**.
