# M3 remaining CPU request budget

Implemented the narrow M7 runner handoff: `ExecutionRequest.remaining_cpu_seconds: float | None = None`. Root approved that exact field for retained M7 owner `/root/m7_learning` after runner checkpoint `d3ee48b`. The optional finite positive value must not exceed the admitted `SandboxPolicy.cpu_seconds`. Omission keeps the existing policy cap; the image, CPU rate/cgroups, recipe, dependencies, filesystem/source policy and isolation are unchanged.

The effective threshold belongs to the complete execution session and its cumulative Docker cgroup CPU counter, including source staging, dependency setup, requested command, in-container observation probes and source capture. It is persisted before create in `record.binding.effective_cpu_seconds` and recorded numerically in execution/export receipts. Final ordinary-exit polls check cumulative CPU before command completion or source publication. CPU exhaustion during staging, setup or export raises the typed internal `CpuBudgetExceeded` and returns `cpu_limit`/`candidate` with the exact last-confirmed source. Actual monitor, storage and cleanup failures remain infrastructure, including when cleanup fails after budget exhaustion. Recovery preserves a prior operation's recorded cap and is not blocked merely because a later policy is stricter; that exception permits cleanup, not new execution admission.

CPU-only tests use explicitly labelled session/HTTP doubles for phase attribution and no Docker/native/model execution. They cover finite/default/fractional/over-policy caps, cumulative versus default thresholds, staging/DEPS/command/export exhaustion, last-confirmed preservation, terminal export polls, monitor/storage/cleanup precedence and recovery under a stricter later policy. Initial API tests retained **17 failed, 4 passed**; a further recovery test exposed and fixed rejection of cleanup under a lower later policy. Final focused result: **40 passed in 0.09s**. Command: `PYTHONPATH=src .venv/bin/python -m pytest -q tests/test_environment_cpu_budget.py tests/test_environments.py`. Exact final output, source/test hashes, UTC capture times and exits are in [verification.json](../evidence/M3/cpu-budget/verification.json).

Exactly one requested actual cap diagnostic ran, with its trusted boundary qualification first: `PYTHONPATH=src .venv/bin/python docs/evidence/M3/cpu-budget/cap_diagnostic.py` (exit0). It used the existing image and cached six wheels with inert synthetic Click source, one development request and no historical B/H build/test matrix. A **0.05 CPU-second** threshold was exhausted during staging; the requested command never started. The result was `cpu_limit`/`candidate`, last-confirmed source unchanged, exact effective cap 0.05 in receipt/binding and verified cleanup. Policy remained 60 CPU seconds and the kernel rate remained 0.5 CPU. The diagnostic took 2.446s and observed cumulative CPU **0.138736s**, an overshoot of **0.088736s**. Full command, source/recipe/policy, maximum memory/CPU, actual owned identity and removal evidence remain in [cap-result.json](../evidence/M3/cpu-budget/cap-result.json); both qualification and request records are removed with empty recovery.

This closes the missing request-to-session budget interface, not the uncertainty inherent in a sampled watchdog. It does **not** establish an exact kernel aggregate CPU-time guarantee: existing ~0.2-second sampling, fixed probe execution and cleanup latency can overshoot, especially for very small remaining budgets. Controller CPU and GPU work are outside this worker counter; cleanup remains separately bounded and is always attempted. M7 must preserve observed costs/overrun rather than describe the threshold as exact consumption. No real inference/model, native provider, human call, download, remote/paid compute or GPU execution occurred. GPU results remain deferred/unverified. This implementation change does not consume a candidate/environment setup repair.
