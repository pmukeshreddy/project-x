**Minimal later boundary, proposed only.** This proposes responsibilities, not an implemented API or a change to M0 schemas:

1. A human or separately authorized trust administrator supplies the reviewer's public key, exact principal, independently checked fingerprint/identity association, authority scope and enrollment evidence through a channel outside model-controlled task evidence. The trust root and enrollment update path must be outside model write authority; a repository allowlist editable by an agent is insufficient. The controller consumes a frozen trust-policy snapshot and current revocation information. Agents cannot create or modify enrollment, obtain the private key or invoke signing for real evidence. Do not accept trust configuration from the submitted attestation. Prefer exact principals and an exact dedicated production namespace, without wildcard or certificate-authority enrollment in the first implementation.
2. After actual controls and the review package exist, the controller freezes exact signing bytes containing format/domain version, full `T0` reference, reviewed-package reference, policy version and content digest, enrolled identity, explicit human decision and a controller-issued challenge bound to that tuple. Any expiry is also signed and checked against a trusted current time. The human reviews the readable package and signs those exact bytes outside agent control, then returns only the detached signature. `HumanReview.attestation` can reference the immutable signed payload and signature envelope. Signing the future `Q` digest would create a cycle and is unnecessary.
3. A verifier receives that attestation reference, the independently resolved expected tuple and controller-owned trust snapshot. It checks strict envelope/canonical bytes, complete reference types/versions/visibility, exact task/package/policy/challenge/identity/decision equality and current signer authorization before and after native verification. Run the pinned absolute executable with an argument array, fixed namespace, explicit immutable allowlist/revocation files and bounded subprocess I/O/time. Accept only successful `-Y verify`; do not parse a success-looking stdout string or permit submitter-selected `verify-time` to bypass validity. Native key-validity checks do not validate an application payload's expiry.
4. M5/M6 atomically record challenge/attestation consumption for the frozen subject/package/policy tuple and enforce admission policy. An identical retry can return its prior result idempotently; it cannot increment human/control/reset counts. Reuse for a different tuple, changed evidence, expired challenge or unauthorized purpose is rejected even when SSHSIG remains valid. Current revocation/quarantine must prevent an old result from restoring admission. Duplicate handling must use the challenge/semantic tuple and stored attestation identity, not merely detached-signature bytes. Actual control/reset runs remain separately identified execution receipts.
5. Missing or mismatched evidence, unknown/unverified enrollment, model origin, malformed signatures, revoked authority and failed verification leave qualification provisional or blocked under the applicable policy. Known-invalid evidence cannot be promoted by a successful native signature. Future verification receipts should retain the executable, trust snapshot, namespace, signed-byte and signature digests, command/exit, trusted verification time and decision; they do not prove human minutes or semantic correctness.

The smallest later human action is to supply a verifiable enrollment association once, then review the completed package and sign its frozen attestation payload.
